# Dwira — AI interior design (Android · iOS · Web)

One Expo codebase (SDK 57, Expo Router, TypeScript, NativeWind, Zustand, i18next, Reanimated).
Hybrid app: content repositories retain their existing mock/local implementation. User sessions, credits, image spaces, requests and admin notifications use the Postgres-backed API in `server/` (served on Vercel through `api/index.js`).

## Android app (APK)
Download the latest APK from **[GitHub Releases](https://github.com/elqaddaoui/interior-design-app-ui/releases/latest)**.

```bash

npm run web           # web only (responsive: centred layout, desktop top nav)
```

- User app: `/` · Admin panel: `/admin`. Default login everywhere (real and demo mode): user `admin` / password `admin`. Custom server credentials (`ADMIN_EMAIL` + `ADMIN_PASSWORD_HASH`) also work in addition.
- Languages: Moroccan Darija (default, RTL), Arabic (RTL), French — Settings → Language.
- Admin edits write to the same Zustand store the user app reads, so they apply instantly.
- Tool-card picture animation (Admin > Tools > card > Multiple images): one engine for every card. Two identical layers (front = visible, back = hidden) share ONE progress value; only the next picture is loaded, into the hidden layer, and a transition starts only once it is fully loaded. 61 transitions (0 cross-fade + 30 wipes, rectangles, circles + 30 creative ones) in four tiers (Safe, Medium, Heavy, Creative); **Transition availability** in the card popup enables each one and says whether it may run on low-end phones (`src/lib/toolCardFx.ts`), and **Test on this phone** reports the average frame time, dropped frames and a Smooth/Borderline/Slow verdict. Low-end phones fall back to the cross-fade; the classification (`src/lib/deviceTier.ts`, pure and unit-checked) combines three layers: **preferences** (reduce-motion, data saver), **hardware facts** (Android RAM <= 2.4 GB is fixed low-end; a 3 GB phone, a 32-bit-only phone or Android 8 and older start on probation; modern phones, iPhones and browsers that hide their specs are never condemned) and **frame times measured on the device** (first frames of each transition ignored, a verdict needs several transitions: 3 janky out of the last 6 demote, 4 smooth promote, the evidence expires after 7 days; the admin can reset it). The old rule (expo-device `deviceYearClass <= 2017`) is gone: that Facebook library stops at class 2016, so every Android phone was treated as low-end, and one cold-start hiccup condemned a phone forever. Every card with any part on screen animates (even a few pixels); cards outside the viewport, other tabs and a backgrounded app pause and keep a still picture, so no CPU is spent on them (`useOnScreen` in `src/lib/toolCardPerf.ts`). The **Transition availability** popup lists the four tiers (Safe, Medium, Heavy, Creative) as tri-state checkboxes that check / uncheck every transition of the tier, and the slideshow picture grid shows 4 pictures per row on every phone. Uploaded card pictures are **never cropped**: each keeps its original aspect ratio (thumbnails in the form and in the picture grid show the whole picture) and is only optimised to WebP, 800 px wide at most; the card centre-fills it when it is displayed. The **Creative** tier (ids 31-60, off by default, skipped on low-end phones) has 30 star-free transitions built from small flat pieces (dots, rings, diamonds, plus signs, bars, triangles in white and / or the accent colour) that ride the window: comet tails, bead curtains, scanners and waves along a wipe edge (with ribbon, glow, colour-bar and shine edges and rubber-band / bounce / snappy easings), spinning windows (a rectangle that turns while it grows, from the centre, a corner or turning back), rectangles from an edge, and irises with orbiting, beaded or bursting pieces from the centre, an edge or a corner. Every piece position comes from one pure function (`decoAt` in `src/lib/toolCardFx.ts`, UI-thread worklet, transform + opacity only, no layout / blur / mask); the video renderer draws the same pieces on a canvas. Elastic and bounce eases overshoot, so a wipe container has a trailing spare and never exposes the previous picture. Try them in the card popup and keep or remove each one in **Transition availability**. `npm run check:toolcards` checks the maths; `node scripts/check-toolcard-browser.js` samples the live DOM of a demo web build (`EXPO_PUBLIC_BACKEND_MODE=demo`).
- **Animation Studio** (Admin > Appearance > Animation Studio, `/admin/studio`): a live editor for the tool-card transitions, Elementor-style. A stage plays the real engine on sample pictures (or the pictures of the chosen card) with play / pause / replay / loop / scrub, and every change shows up at once; **Submit** stores it, **Discard** drops it, and the same style is also what the Home cards play. Six tabs: **Transition** (force one transition on every card, seed, accent colour), **Motion** (easing: the classic ones plus linear, anticipate, steps, cubic-bezier and spring with a live curve; direction fixed / alternate / random; edge sweep; window origin; photo zoom-in, zoom-out and push), **Bar** (the white bar: size, solid / double / dashed / dotted, white / accent / custom colour or gradient, opacity, glow, trail, rounded ends, fade; on a rectangle or spinning window it is the frame, on an iris the ring), **Elements** (stars, circles, hearts, sparks, hexagons, moons, bolts or a mix; count, size and size variation, spin, glow, pulse, stagger, colour mode or palette; motion type: follow the transition, random, burst, rain, rise, drift, swirl or twinkle), **Colour** (a solid or gradient colour wash that blooms and fades) and **Looks** (12 ready styles, *Surprise me*, undo / redo, reset, copy / import a style as JSON). The style applies to all cards (`settings.toolCards.studio`) or to one card only (`tool.media.fx.studio`, replaces the global one); a default-valued style is plain, so nothing changes until you edit. Everything is transform + opacity on the UI thread, low-end phones skip the photo zoom and the extras, and the pre-rendered MP4 videos draw the same bar, pieces, wash, easing and photo motion on a canvas (the style is part of the video signature, so changing it marks the videos outdated). The model and its sanitiser are in `src/lib/fxStudio.ts`; `npm run check:toolcards` covers easings, overrides, photo motion, every piece motion on every effect, plumbing and signatures; `npm run check:studio` (needs a demo web build served on port 4173) drives the Studio in a real browser, LTR and RTL.
  - **Library and saved looks** (Looks tab): 30 clean ready-made before / after looks in 6 categories (Minimal, Cinema, Luxury, Tech, Fun, Nature, 5 each; `LIBRARY` in `src/lib/fxStudio.ts`). One click forces the look's transition and sets its whole style, everything stays editable. **Save this style** stores the current look under a name in the admin's own preferences (`admin_prefs.studioPresets`, max 60, validated by `server/content.js`, private to the admin and shared across their devices), with apply / delete.
  - **Stage pinned while scrolling**: the preview stays in view on desktop (sticky column) and on phones (pinned strip above the controls), so every change is seen on the same screen.
  - **Instant first card** (`settings.toolCards.instantFirst`, default on, switch in Studio > Device and first load): the first Home card skips its first hold, mounts at once without waiting for the visibility observer and warms the first two pictures, so its first transition starts as soon as both pictures are ready. Off = the usual hold. The same card shows the device verdict and the **Reset detection** button (same as the availability dialog).
- Admin panel shortcuts: **right-click** (mouse) on any row, tile, menu entry or the page background opens a context menu (edit, duplicate, show/hide, move first/last, select, delete; WhatsApp/call/copy on clients and requests; open in a new tab on menu entries). Touch long-press keeps selecting rows as before. Every collection row also has a **Duplicate** button (and a bulk Duplicate for the selection); campaigns, slideshow pictures and palette colours can be duplicated too. Each admin page shows the configured loading animation until its data has arrived from the database. Search/filter inputs and API-key fields are not auto-filled by the browser (`autoComplete` is off / `new-password`); saved keys stay on the server untouched.
- Multiple-images popup (Tools > Edit > Multiple images; it fills the full screen height): **card height, text zone and text placement (inside / outside the picture) are global** - one change updates every card (same `settings.toolCards` selector approach for all three); per card: animation, **pause 0-5 s** and **speed 0.2x-2x** (sliders, 0.1 steps, clamped when read), gradient. ## Data: everything lives in the database
With the backend enabled (default on web, or `EXPO_PUBLIC_API_URL` on native) the app keeps **no local copy** of business data. `src/data/repositories/index.ts` wires every repository to the API:

| Data | Table(s) | Who writes it |
| --- | --- | --- |
| Content: `tabs`, `tools`, `roomTypes`, `styles`, `palettes`, `sections`, `categories`, `inspirations`, `models`, `plans` | `content_items` | admin (`PUT/DELETE /api/admin/content/...`) |
| Settings documents: `branding`, `theme`, `assistant`, `settings` | `content_docs` | admin (`PATCH /api/admin/doc/:name`) |
| Auto-translation: `POST /api/admin/translate` (admin only) fills the other languages of multilingual fields (Darija / Arabic / French) with free, keyless providers: Pollinations LLM first (real Darija), MyMemory fallback (fr<->ar). Toggle: Admin > Interface > Automatic translation (`settings.autoTranslate`). | - | admin |
| Clients (leads), credits, blocked state | `clients` | clients sign in; admin edits credits/blocked |
| Render requests | `requests` | clients create; admin updates |
| Per-client history and chats | `space` | the client |
| Notification / banner / language preferences | `clients.prefs` (clients), `admin_prefs` (admins) | the person, from any device |
| Push devices | `subscriptions` (owner = admin id or client id) | the person, per device |

The starter content in `server/seed-content.json` (generated from `src/data/mock/seed.ts` with `npm run gen:seed`) is inserted **once** into an empty database (`content_seeded` marker); after that edits and deletions are permanent. Provider API keys are only returned to admin sessions. Only truly device-local values stay on the device: the anonymous device token, the "admin session exists" flag, and in-progress UI state. `EXPO_PUBLIC_BACKEND_MODE=demo` restores the old AsyncStorage mocks for offline demos only.

### Real-time sync
`GET /api/sync` returns a version counter per kind of data (`content`, `requests`, `clients`, one per client, one per admin). Every device polls it every 4 s (and on focus/visibility/reconnect) and reloads only what changed: admin edits appear on all admin and client devices, new leads/requests appear on every admin device, credits/blocks/history reach the owning client on all of their devices. Unsaved admin drafts are never overwritten. (Websockets are not available on Vercel serverless; polling is the portable real-time channel. The same poll also retries failed notifications.)

### Uploaded images
All media (admin images and videos, client photos, AI results, chat images, external image links) is stored in **Cloudflare R2** through `server/media.js` and referenced by stable `/api/media/<hash>.<ext>` URLs (a redirect to the public R2 object). Videos use admin-only presigned uploads; external https images are downloaded once. Without the `R2_*` variables, files fall back to raw bytes in the `media` table; base64 is never stored. Setup and migration (`scripts/migrate-media-to-r2.js`): see [docs/r2-setup.md](docs/r2-setup.md).

## Services to replace later (`Services`)
`upload` (file storage) and `whatsapp` (send design) are still mock services; `render` is real as soon as an image engine has a key (see **AI image generation** below; without one the app keeps its sample result); `auth` is the real admin login and `chat` is real (see **AI chat** below; it falls back to the local canned reply when no provider answers).

## Deploy on Vercel (UI + API)
`vercel.json` builds the static web export **and** exposes the backend as a Vercel Function (`api/index.js` -> `server/index.js`). The backend needs a Postgres database; without one every `/api/*` call answers `503 DATABASE_NOT_CONFIGURED` and `/lead` shows "service temporairement indisponible".
1. Import the repo in Vercel (framework preset: **Other**); install/build/output are set in `vercel.json`.
2. **Project -> Storage -> Create Database -> Neon (Postgres)** and connect it to the project (Production + Preview). Vercel injects `DATABASE_URL` / `POSTGRES_URL`; tables are created automatically on first request.
3. Redeploy, then open `https://<your-domain>/api/health`: it must return `{"ok":true,"database":"pg",...}`. Then test `/lead`.
4. Admin login at `/admin`: `admin` / `admin` by default. For real credentials set `ADMIN_EMAIL` + `ADMIN_PASSWORD_HASH` (`ADMIN_PASSWORD='...' node server/password.js`) and then `DISABLE_DEFAULT_ADMIN=true`.
5. Optional environment variables: `CRON_SECRET` (protects `/api/push/pump`), `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY` / `VAPID_SUBJECT` (otherwise generated and stored in the database), `FCM_SERVICE_ACCOUNT_JSON` (native Android app). See `server/.env.example`.
6. Node 22.13+ is required (`engines` in `package.json`).

## Deploy on Hostinger (managed Node.js, UI + API in one process)
Build command not needed (`dist/` is built by `postinstall` during Hostinger's `npm install`; `npm run build:web` also works), entry file `server/start.js` (= `npm run start:server`), output directory **empty**, Node 24, one required variable: `DATABASE_URL` (Neon pooled). Exact hPanel settings, all variables and troubleshooting: [docs/HOSTINGER.md](docs/HOSTINGER.md). Vercel keeps working unchanged; `vercel.json` and `api/` are Vercel-only.

### Performance (first load)
What keeps the first load fast, and where to change it:
- **The UI never waits for the network.** Home renders as soon as the device-only reads (language, local flags) are done. Public content comes from, in order: the HTML shell's early request (`scripts/postexport.js` injects a `fetch('/api/content')` that starts before the JavaScript has downloaded), the copy cached on the device (`dwira:v1:content-cache`, public content only, never an admin copy), then the network. With nothing cached, Home shows same-size placeholders (never a false "empty" message). The session check runs in the background. Startup reads retry at most 4 times (0.8 s, 1.6 s, 2.4 s) and then the app stays open; the 4 s sync loop keeps trying.
- **API.** `vercel.json` pins the function to `fra1` (next to the Neon database in Frankfurt). `/api/health` and the public `/api/content` skip the session/auth lookup (an admin credential or `?a=1` is the only thing that triggers it). Tables are created only when the stored schema marker (`settings.schema_version`, a hash of the schema) differs, not on every cold start.
- **`/api/content` caching.** Public responses carry `Cache-Control: public, max-age=0, s-maxage=<CONTENT_S_MAXAGE>, stale-while-revalidate=<10x>`; `CONTENT_S_MAXAGE` defaults to 30 seconds, is capped at 300 and `0` disables shared caching. Admin requests (`?a=1`, or any credential) are always `private, no-store`: that copy contains provider API keys. After an admin edit, devices reload with `?v=<version>` so the short CDN window never delays a change they were told about.
- **Bundle.** The gesture library (before/after slider, admin drag handle) is an on-demand chunk; the web gesture root no longer imports it. The Home route chunks are preloaded from the shell. Unused packages were removed.
- **Assets.** The web icon font is subset to the glyphs the app can use (`python3 scripts/subset-icons.py`, needs `fonttools` + `brotli`; re-run it if you add icons to `ICON_CHOICES` or the seed). The first Home card image is `fetchpriority=high`/eager and preloaded by the shell once the content names it. Hashed files under `/_expo` and `/assets` are immutable for a year; icons/favicon are cached for 30 days, the manifest for a day, `index.html` always revalidates (same policy in `vercel.json` and the Node server).
- **Measure it.** `node scripts/measure-lcp.js <url> --runs=5 [--images=allow] [--cpu=4]` runs a cold-cache load on emulated Slow-4G (1.6 Mbit/s, 150 ms RTT) and prints LCP/FCP/bytes. It is a lab figure from your machine; use PageSpeed Insights for the real one.

### Notifications
- **Admins** get a push for every **new lead** (a client signing up) and every **new render request**, on every device where notifications are enabled. Open `/admin` -> **Activer les notifications** then **Envoyer un test**.
- Admins also get a push for every **new chat message** from a client. It opens `/admin/chats` on that conversation, where the admin can reply (or open WhatsApp). The reply is saved in the client's own conversation and pushed to that client only (opens `/chat/<id>`).
- **Clients** get a push when their design is **ready** (the admin marks the request delivered), and when an admin **replies in chat**, on every device where they enabled notifications.
- **Notification switches** (`/admin/notifications`, stored in `settings.notifyAdmins` / `settings.notifyUsers`, both on by default, saved with Submit): one for admin notifications, one for user notifications. They are checked on the server for every delivery path (requests, leads, chats, replies, ready, test push), on top of each person's own preference. When user notifications are off, the Settings toggle is disabled with an explanation. The same page lists the clients who enabled browser/app notifications with a status (on, off by the client, paused by the admin).
- **On by default:** whenever a device already has notification permission and the person's saved setting (stored in the database, per admin / per client) is not "off", the device is subscribed silently on sign-in or startup, with no prompt. Turning notifications off in Settings is saved in the database and applies to all of that person's devices. The browser/OS permission prompt can only be shown from a tap, so first-time opt-in is the toggle in Settings or the banner in History.
- Works on desktop Chrome/Edge/Firefox/Safari, Android Chrome, and the Android app. On iPhone/iPad, first use Safari **Share -> Add to Home Screen**, open Dwira from that icon, then enable notifications (Apple only allows web push for installed web apps).
- Delivery is sent from the API request itself (bounded wait); failures stay in the outbox and are retried by the sync poll and the daily cron (`/api/push/pump`, Vercel Hobby allows daily crons only).

### Push campaigns and automations (`/admin/notifications`)
- **Campaigns**: one-off (now or scheduled), or recurring (daily / weekly / monthly) with title and body in Darija, Arabic and French (`{name}` is replaced by the client's first name), an in-app link, and an audience: everyone, **new** clients, **existing** clients, **inactive** clients, clients who **generated images** (or never did), and/or hand-picked people. The composer shows the reachable device count and can send a test push to your own devices.
- **Automations** run on activity: after sign-up, after a first/each design, or after inactivity, with a delay, a per-client cooldown and the global frequency cap (`settings.campaignCapHours`, default 24 h). Quiet hours default to 22:00-08:00 Africa/Casablanca. Every delivery is recorded once per client and occurrence (`campaign_deliveries`), so retries and parallel runs never double-send.
- **Scheduler**: Vercel Hobby only allows a daily cron, so due campaigns are also processed by every sync poll, by `/api/push/pump` and by an in-process timer. For minute-level punctuality, point a free external pinger (cron-job.org, UptimeRobot) at `GET /api/push/pump` every minute, with `Authorization: Bearer $CRON_SECRET`.
- The push card on the dashboards (admin home, requests, notifications > Devices) shares one minimal component.

### AI image generation (`POST /api/ai/render`)
- **Inputs, all working for text-to-image and image-to-image:** the client's photo (or, with no photo, a written description), the room type, the style preset, the Explore inspiration (sent as a style reference, never as the room), a preset palette or up to 5 **custom hex colours** (applied exactly, with roles for walls / furniture / accents), the mode (restyle keeps the layout, renovation allows more freedom) and the client's own instructions (500 characters).
- **Interior accuracy:** `server/imagegen/prompt.js` builds a structure-preserving prompt (room layout, walls, openings, perspective, proportions, furniture footprint, materials) and the output keeps the photo's aspect ratio (multiples of 16, longest side `IMAGEGEN_MAX_SIDE`, default 1024).
- **Default engine: Pollinations** (`gen.pollinations.ai`, free models). Photo models: FLUX.2 Klein, FLUX.1 Kontext, MAI Image 2.6 Flash. Text-only models: Z-Image Turbo, FLUX.1 Schnell. It needs **one free key** from <https://enter.pollinations.ai>: set `POLLINATIONS_API_KEY` or paste it in **Admin > AI models** (write-only, stored server-side, never returned to any client). Without a key the app stays in demo mode and shows its sample result.
- **Any OpenAI-compatible images API** (`/images/generations` + `/images/edits`) works too: `IMAGEGEN_API_KEY` / `IMAGEGEN_BASE_URL`, or set an **engine** (and optional API URL / key) on an admin AI model. To add a different kind of engine, add one entry to `ENGINES` in `server/imagegen/index.js`.
- **Active model & switching:** the wizard's last step shows the model that will run. The admin picks the model per tool (Admin > AI models); turning on *Let the client choose the model* shows a switcher limited to the models that tool allows. The admin's model runs first, then the free chain (a failing or rate-limited model rests for a while and the next takes over). Optional: `IMAGEGEN_MODELS_I2I` / `IMAGEGEN_MODELS_T2I` (comma-separated model ids put in front of the chain).
- **Safety:** one generation per request (idempotent per claim id, so retries never generate or charge twice), owner-checked, max 2 concurrent per client; the photo and result go through the media store (R2 or the database).
- **Time limit:** Vercel stops functions after 30 s, so there the budget is 25 s (`IMAGEGEN_BUDGET_MS` / `IMAGEGEN_ATTEMPT_MS` override it). Hostinger / any long-running Node host gets 54 s per request. Prefer a long-running host for the slower photo models.
- **Prompt cards (`/admin/prompt-cards`)** - the admin decides the final text and pictures sent to the image model. One screen, three ideas: **pick a card, change one thing, watch the prompt change.**
  - *Scope strip* (top): **Explorer** (white tile), **All tools** and one tile per tool (its picture, a *Custom* badge when it has its own steps). Everything below belongs to the selected tile.
  - *All tools* has five tabs, each with a dot when it differs from what the app sends by default (a fresh install shows no dot): **Rules** (free text sent as a mandatory `DESIGN RULES` block, with one-tap rule ideas and a character counter), **Images** (room type and style sent as *Text*, *Image* or *Both*), **Steps**, **Words** (own English wording of a style / room type; the default wording is shown as the placeholder, kinds sent as image-only are hidden) and **Output** (language of the client's brief, max image side).
  - *Steps* are the blocks of the prompt (task, structure, brief, mode, composition, intent, style, style/room image, palette, quality, rules, final check): drag to reorder (same drag handle as every admin list, or the move buttons), switch off what you don't need, tap one to re-word it. Tap a `{variable}` chip to insert it at the end; an unknown `{name}` is flagged; *Original text* restores the default; an *Edited* badge and a green *live* dot show what was changed and what the current test case really uses. The default wording is the one the app always sent: **with no customisation the prompt is byte-identical** (golden fixtures in `scripts/fixtures/prompt-defaults.json`). The **style image** and **room image** steps are *automatic* (off by default, on by themselves when that picture is sent; an explicit switch wins) and only show the text field of the chosen type.
  - *A tool tile* shows **Same as All tools** (steps locked, read-only) or **Custom**. *Customise* starts from a copy of the shared steps, *Back to All tools* removes the override (and brings it back, with your edits, if you customise again before saving), *Copy from...* reuses the steps of another tool (a copy, not a link). A tool only ever holds its steps: rules, pictures, output, words and the Explorer picture are shared.
  - *Explorer tile*: *Applies to* (every generation, or Explore only), the extra rules used only when the client generates from Explore, and the wording of the Explorer-picture step. **The Explorer picture is always sent** when the client generates from Explore; it is capped by what the model accepts (`cap.refs`).
  - *Live preview* (right column on desktop, below on a phone), **always on** and updated 0.45 s after each keystroke - no button. It is a **fake generation** (`POST /api/admin/prompt-rules/preview`, admin only): same planning as a real run, no engine call, no credit, input is always a client photo, unsaved edits included. A collapsible **test case** (tool, style, room - filtered to the tool's group -, palette, Explorer picture, Relooking / Rénovation when `modeChoice` is on, client brief) says what it is generated for. The prompt is shown as one passage per step: **touch a passage to jump to the step that writes it**. Below: pictures sent / not sent (and why), palette colours, model and size, warnings.
  - *Saving*: a floating bar appears only for a real change (trailing spaces or re-typed default wording are not changes - `normalize` mirrors the server's `cleanRules`), with **Save** and **Discard**; leaving with unsaved edits asks first.
  - Code: pure, unit-checked model in `src/lib/promptCards.ts`; screen `src/app/admin/prompt-cards.tsx`; pieces in `src/components/admin/promptcards/` (`ui.tsx`, `Editors.tsx`, `LivePreview.tsx`); texts in `src/i18n/locales/promptcards.ts` (fr / ar / dar, same keys).
  - Rules are stored server-side in `settings.prompt_rules` (never in the public content) and always sanitised (`server/imagegen/rules.js`). The admin catalog (`GET /api/admin/prompt-rules`) also returns the default style / room wording (`catalog.vocab`). Each request's *AI run* (Admin > Requests) records the pictures really sent and where the rules came from.
- **Relooking / Rénovation choice** (Admin > Interface > *Choix Relooking / Rénovation*, `settings.modeChoice`, on by default): shows or hides the mode cards on the last wizard step. When hidden the mode is **Relooking everywhere** - the wizard, re-generation from History, the Prompt cards preview and the server prompt (`server/imagegen/index.js` forces `restyle`, so even an old draft is a Relooking).
- Tests: `node --test --test-concurrency=1 scripts/check-imagegen-server.js scripts/check-prompt-rules-server.js` (engines are mocked, no network); `npm run check:promptcards` (the Prompt cards model, incl. parity with the server's `cleanRules`); `node scripts/check-promptcards-browser.js` drives the screen in a real browser, LTR + RTL, desktop + phone (build the web export, run `PORT=8080 node server/start.js` with the default admin login, set `SHOTS=dir` for screenshots).

### Database transfer (Neon free tier)
Network transfer is the bytes Postgres sends back. What was reduced (measured with `scripts/bench-db-transfer.js`: **48,340 KB -> 1,961 KB** for the same scripted session, 96% less): media is read metadata-first with an in-memory byte-budget cache (`MEDIA_CACHE_MB`, default 24) and `HEAD`/`304` support; `/api/content` answers `304` from a version-keyed snapshot (ETag) without touching the tables; per-user and guest reads fetch one row (not the whole space); client sync is per part (`c:<id>:history|requests|conversations`) so one change reloads one list; the admin inbox is the newest 300 chats plus a `since` delta; `/api/requests` is bounded (`?limit=`, `?before=`). Everything else (schema, endpoints, payload shapes for existing clients) is unchanged. Tests: `node --test scripts/check-neon-transfer.js`.

### AI chat (`/api/chat/reply`) and Admin > Assistant
One customer message goes through three steps (`server/assistant/index.js`): **1.** the owner's **automations** (the first enabled one that matches answers), **2.** otherwise the **AI**, grounded on the app knowledge base, **3.** on error, quota or timeout the next provider of the chain takes over (24 s budget for the whole chain). Every reply carries `meta` (`status` automation / active / fallback / paid, provider, model, and the providers that failed before). Only admins see it: a badge under each assistant message in `/admin/chats`.

- **Free providers (default), ranked** for Moroccan Darija (Arabic or Latin letters), Arabic and French: **Google Gemini** (`GEMINI_API_KEY`, aistudio.google.com), **Mistral** (`MISTRAL_API_KEY`, console.mistral.ai), **Groq** (`GROQ_API_KEY`), **OpenRouter** free models (`OPENROUTER_API_KEY`), then keyless **Pollinations** as a last resort. Keys can be environment variables or pasted in `/admin/assistant > AI providers` (write-only, stored server-side, never returned). Each free provider can be switched off. Optional: `CHAT_PROVIDER_ORDER`, `GEMINI_MODEL` / `MISTRAL_MODEL` / `GROQ_MODEL` / `OPENROUTER_MODEL`, `CHAT_RATE_LIMIT` (messages per minute per visitor).
- **Paid providers (optional, separate zone)**: OpenAI, Claude, DeepSeek, Mistral, OpenRouter or any OpenAI-compatible HTTPS endpoint (up to 6). Each has its own key, model and switch. It stays **off until a key exists**; the admin chooses whether the paid zone runs **before** or **after** the free one. Keys are write-only (`settings.chat_paid_keys`), the config lives in `settings.chat_config`. The page shows each provider's state (ready / active / failed / resting), the last failure reason and the resulting order.
- **Knowledge base**: `docs/APP_KNOWLEDGE.md` (curated, multilingual) plus data read from `server/seed-content.json` (tools, rooms, styles, palettes) and the customer screens are built into `server/knowledge/kb.json` by `npm run build:knowledge` (`npm run check:knowledge` fails when it is stale). The AI receives only the relevant facts, answers in the visitor's language, never sends the visitor to "the owner", and says so when it does not know. The admin can add own facts (hours, delivery area...) in `/admin/assistant > Knowledge` (`assistant.knowledgeNotes`).
- **Automations** (`/admin/assistant > Automations`, `GET|PUT /api/admin/assistant/automations`): name, trigger (keywords, intent, first visit, schedule in the Morocco time zone, quick-reply button), reply (fixed text, template with `{name|fallback}` `{app}` `{credits}` `{date}` `{time}` `{greeting}`, or written by the AI from the admin's instructions), language (Darija / Arabic / French / auto), on/off, once per chat. List order is the priority; reorder by drag or arrows, duplicate, delete. Each one has a usage counter and last-used date. The **test box** (`POST /api/admin/assistant/test`) previews a draft or the real pipeline without counting anything. Button triggers show as quick-reply chips above the chat box (`GET /api/chat/buttons`).
- The reply language follows the visitor (Darija in Arabic script or Latin letters, Arabic, French).
- **Human-like pacing** (`/admin/assistant > Behaviour`): *Instant*, *Natural* (delay scales with the answer length, 0.9-3.5 s) or *Custom* min/max seconds, plus an optional typewriter reveal. The typing indicator shows immediately; the request starts at once and its own network time counts towards the delay.
- Checks: `npm run test:server` (`check-assistant-server.js`, `check-chat-reply-server.js`), `npm run check:assistant` (admin model + texts), `npm run check:assistant:browser` (web export, fr desktop / ar phone / dar desktop).

Why `scripts/postexport.js`? Vercel never serves paths containing a `node_modules` segment, but `expo export` writes package fonts/images
(icon font, router icons) to `dist/assets/node_modules/...`. The script moves them to `dist/assets/vendor/...` and rewrites all references, injects the web app manifest/iOS meta tags, and fails the build if any are left.

## Admin: request details, picture viewer, WhatsApp-style chat

- **Design requests (`/admin/requests`)**: each request shows everything the client chose (tool, room, style, mode, palette, exact colours with their roles, description and its English translation, inspiration) and everything the generation used: model requested, model used, every model tried, size, duration and the exact prompt. The server records this as `aiRun` on the request row (success and failure). It is stripped from every client-facing endpoint. Requests made before this feature only show the saved draft.
- **Picture viewer (`src/components/ui/ImageViewer.tsx`)**: opens at the tapped picture at its original size (shrunk only if it does not fit the screen), swipe left/right (arrows or arrow keys on desktop) for the other picture, a zoom button for 1:1 pixels, and save. It is used for the request photo / AI result / final design / inspiration, the list thumbnails and the chat pictures.
- **WhatsApp-style chat (`src/components/chat/WaChat.tsx`)**: text, voice notes (expo-audio), several pictures sent with a caption, one tap on a picture opens the viewer. The admin turns it on or off in **Admin > Interface** (`settings.waChat`, on unless false); off = the classic `ChatView`. Voice notes are stored as media (`/api/media/<hash>.weba|m4a|mp3|ogg|wav|aac`, type checked from the bytes, `MEDIA_MAX_AUDIO_MB` default 8, Range requests supported) and appear in the admin chat inbox.
- Generation fidelity is covered by `scripts/check-imagegen-server.js` (six different generations check that every client choice reaches the model prompt and the `aiRun` record).

## Admin: interface options
- **Loading screen** (`/admin/interface`): on/off, 9 built-in styles (ring, dots, pulse, bars, plus four Moroccan-interior ones: zellige tiles, horseshoe arch, fanous lantern, mosaic wave) + a custom image (GIF/SVG/PNG/WebP, optional spin/pulse), colour, and display time. **Auto** (default) removes it as soon as the first two Home cards have painted; a fixed time (0.5-10 s) keeps it that long after opening. The same loader is shown whatever page the app opens on, and every in-app spinner (buttons, loading placeholders, large images) uses it too (`<Spinner/>`). On web it is plain HTML/SVG in `index.html` (painted before any JavaScript, see `src/lib/loaderShell.js`); native draws the same styles in React (`BootOverlay`).
- **Chats**: client conversations are stored per account (database `space` table) and restored on every device the client signs in on; a new account starts empty and the app clears the previous account's data when the user changes. Admin messages cannot be forged or overwritten by a client.
- **Video thumbnails**: when a tool has a video but no image, the first frame of the video is captured automatically (on upload and on a pasted URL; web canvas, native expo-video + ImageManipulator) and used as its preview. If capture fails the form still saves.
- **Dashboard**: 7/30/90-day KPIs with trend vs the previous period, activity chart, search (requests, users, tools, styles, rooms), best features, recent activity, quick actions.
- **Interface & menus** (`/admin/interface`): choose the user bottom bar (Classic / Floating / Minimal) and the admin menu design (**Glide** sliding pill, **Beam** edge light, **Spotlight** hover halo; `settings.adminMenuDesign`), with a switch to turn the menu motion off (`settings.adminMenuAnim`; motion also stops when the device asks for reduced motion). The menu has two sizes only (expanded / icon rail), changed with the collapse icon in the page header; the account (open app, sign out) is one compact row at the bottom of the menu. The exit-confirmation message editor opens on click.
- **Undo / redo for unsaved edits**: the "live preview" bar (and the Animation Studio header) has back / forward icons and Ctrl+Z / Ctrl+Y (Ctrl+Shift+Z too; Cmd on macOS). Edits of one field within 700 ms are one step, up to 100 steps; saving or discarding clears the steps of that draft (`src/lib/draftHistory.ts`, `src/store/adminHistory.ts`, `npm run check:history`).
- **Home tabs** (`/admin/tabs`): switch "show all tools by default" (`settings.homeShowAll`). When on, Home opens on an "All" pill and tabs are an optional filter.
- **Theme** (`/admin/theme`): 20 presets in 6 categories + custom (5 colours, the rest derived with contrast checks). The phone status bar and Android navigation bar take the theme background colour (`SystemBars`).
- The AI model is chosen by the admin per tool (default model fallback); end users never see a model picker.
- **Image optimisation**: every image an admin or a user uploads is optimised in the app BEFORE it is sent to Cloudflare R2 (`src/lib/imageOptimize*.ts`, rules in the pure `imageOptimizeCore.ts`): longest side capped (photos 1280 px JPEG, chat 1024 px WebP, card pictures 800 px WebP, video posters 640 px WebP, admin assets 1600 px WebP with transparency kept), re-encoded until it fits one request. SVG and GIF pass through untouched, and so do pictures that are already optimised. The only images that skip it are the AI-rendered results, which the server stores itself.
- **Performance** (`/admin/performance`) > **Video preview**: renders a short, seamlessly looping, optimised MP4 of each animated card (slideshow with 2+ pictures) entirely in the browser (WebCodecs through `mediabunny`, H.264 first, then VP9 / AV1; `src/lib/cardVideoRender.web.ts`), for one card, the selected cards, or every missing / outdated card. The MP4 is uploaded to R2 (presigned PUT) and assigned automatically to the card (`tool.media.video` + `videoSig`, the signature of its pictures, effects, hold and speed). The option **Include animated elements in the video** (`settings.toolCards.videoExtras`, off by default) also draws every animated element of the transitions into the video - the small white edge bar, knob, glow, colour bar, shine, sparkles, doors, zoom frame, iris ring, flash and the creative pieces (`src/lib/cardVideoExtras.ts`, the canvas twin of `RevealStack`, same maths). **Render quality** (`settings.toolCards.videoQuality`) picks the size, frame rate and bitrate of the rendered videos: *Light* (480 px, 24 fps, for slow networks and old phones), *Balanced* (default, 720 px, 30 fps, a few hundred KB), *High* (960 px, 30 fps) and *Ultra* (1280 px, 60 fps, tablets / big screens; `VIDEO_QUALITIES` in `src/lib/cardVideoPlan.ts`). The extras option and the quality (when not Balanced) are part of the video signature, so changing either flags the videos as outdated. A card whose pictures or animation settings changed is flagged **outdated** and keeps the live animation until it is re-rendered. **When to play the video** is a global setting (`settings.toolCards.videoMode`): *low-end phones* (default), *always* or *never*; the video loops muted, only while its card is on screen, with the first picture as poster, and falls back to the live engine if it cannot play. Videos are rendered once for the app's default direction (RTL). To encode the frames the browser must read the pictures. It first tries a direct read; when the storage has no CORS rule for the admin origin (or the picture is an external link) it fetches the picture through the signed-in admin-only proxy `GET /api/admin/media/fetch?url=...` (own `/api/media/...` files are read straight from storage, external https links go through the same SSRF-guarded downloader as imports), so no R2 CORS setup is needed for rendering (it is still needed for direct uploads, `docs/r2-setup.md`). The native app only plays videos, rendering needs a browser.
  - **Best quality** (`videoQuality: 'best'`): 50 fps at the real card size (card width 360 px x pixel ratio 3 = 1080 px), the file fitted between **1 and 1.5 MB** (the encoder is re-run, up to 5 passes, with a corrected bit rate until the size lands in the window; a simple card may stay under the minimum, which is reported). **Advanced rendering settings** (collapsible panel, `settings.toolCards.videoAdv`, only the touched keys are stored and they are part of the video signature): size (quality / real card size with card width and pixel ratio / custom), fps, size window or manual bit rate, key-frame interval, codec (auto / H.264 / VP9 / AV1). **Estimated size before rendering**: per card and total, with the calculation shown (frame size and fps, loop length, moving vs still frames, target window or bit rate x duration, codec) and a hint of the sharpest width that fits. **Middle-of-the-transition image**: the frame halfway through the first transition, drawn at the chosen size and really compressed with the chosen settings, so the result can be judged before rendering. The maths is in `src/lib/cardVideoPlan.ts` (`resolveRender`, `estimateVideo`), the encoder and preview in `src/lib/cardVideoRender.web.ts`; `npm run check:toolcards` covers them.

## Local full stack
```bash
npm run build:web
PGLITE_DIR=:memory: COOKIE_SECURE=false npm run start:server   # API + dist on http://localhost:8080 (in-process Postgres, no install)
```
`npm run start:server` runs `server/start.js`: one process for `dist/` and `/api/*`, listening on `PORT` (0.0.0.0). It refuses to start without `DATABASE_URL` unless `PGLITE_DIR` is set (`:memory:` or a folder, e.g. `server/data/pglite`). Set `DATABASE_URL` to use a real Postgres instead. The server listens first and connects to the database in the background (retrying while a sleeping Neon database wakes up): `/api/health` answers 503 with `database: "starting"` until then. `/api/health` returns JSON with `ok`, `runtime`, `database` and `adminConfigured`; HTML means `/api` routing is wrong. For a separately hosted API, set `EXPO_PUBLIC_API_URL=https://api-host/api` **before building** (required for Android/iOS) and `APP_ORIGINS` on the backend. To intentionally run the UI-only demo, build with `EXPO_PUBLIC_BACKEND_MODE=demo`.
